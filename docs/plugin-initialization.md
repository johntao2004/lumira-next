# 插件单文件初始化

带数据库初始化的内置插件与 SDK 示例，每个只保留一份 `migrations/V<版本>__plugin_initialization.sql`。没有数据库初始化的插件不添加空脚本。编号表示该最终结构的迁移边界，不表示目录中需要存在此前的逐版 SQL。

主程序 B52 不变。插件继续使用各自的 `plugin_<id>_schema_history`，共享 PostgreSQL 的 public schema。因为该 schema 已含宿主对象，插件使用版本化 SQL，避免 Flyway 在创建 version=0 的历史基线后跳过 B 类型脚本。

## 新安装与重复启动

新安装先登记插件的 version=0 Flyway 基线，再执行唯一初始化 SQL。该 SQL直接建立最终表结构、约束和索引，不依次执行历史 ALTER。权限兼容处理保持原来的数据范围和授权边界，不重新执行曾被宿主禁用的 MFA 权限引导种子。

后续启动通过普通 Flyway resolver 校验当前初始化脚本的名称、描述、版本和 checksum，不重放初始化。卸载保留结构和历史，再安装同样不重放业务写入。

## 已安装的旧包

合并前的已发布包不改写，合并后的包发布新的插件版本。`formatVersion=1` 的 `migrations/initialization.json` 只保存已发布迁移的版本、描述、文件名及原始 Flyway checksum，没有历史 SQL 内容。

如果插件已完整执行旧迁移，宿主先逐条核对原记录，要求所有记录成功、版本齐全且校验和、名称及描述完全匹配，再通过仅用于校验的 resolver 验证历史。不执行新的初始化 SQL，不清空或重建表，不修改历史记录，也不新增冒充已执行的记录。校验用 executor 禁止执行。

如果历史存在失败、未知版本、校验和不符、混合初始化身份或尚未完成的旧版本，升级会失败关闭，不擅自修复或补写记录。历史未完成的安装需要先使用相应已发布包完成原升级，再切换单文件包。不得执行 repair、删除历史、忽略缺失迁移或关闭校验来跳过问题。

没有初始化元数据的已有包及第三方插件仍走原迁移入口，保持兼容。不要修改已发布初始化 SQL 或元数据中的历史身份；结构再次变化时必须单独设计保数据兼容路径。

## 显式向前演进

需要变更已有结构的插件可使用 `formatVersion=2`。目录仍只有一份完整初始化 SQL，新安装只执行该文件。`publishedMigrations` 原样保留已发布增量迁移的身份；`previousInitializations` 保存此前完整初始化的原始 Flyway 身份；`evolutions` 仅包含这些历史边界之后的新变更，版本连续递增，SQL 文本和内容校验和一同发布。

宿主先验证已有历史属于一条完整、成功且校验和匹配的路径，再通过 Flyway 在事务内执行尚未应用的向前变更。旧记录仅用于验证，执行器禁止重放；成功时只追加真实执行的新记录。失败时事务回滚结构与历史，不能用 repair 补救。已经应用的 evolution 也不可修改内容或身份。该机制不处理旧增量历史缺失或混合历史。

支付核心 1.1.0 使用 V5 完整初始化；已有 V4 完整初始化或完整 V1–V4 增量历史，仅追加 V5 渠道标识约束演进，保留订单、配置及原历史。新约束仍限制渠道 ID 格式和长度，渠道可用性与归属由实际加载的支付插件校验。三个约束在同一事务中变更，配置了锁等待和语句时间上限。

## 验证要求

- 每个有初始化的源码目录和发布包均只有一份 SQL，且元数据匹配插件 ID。
- 在独立 PostgreSQL 18 QA 数据库分别验证原迁移链和新初始化，比较最终列、默认值、约束、索引及权限。
- 对已完整迁移且含模拟业务数据的数据库执行新包初始化入口，业务内容指纹和已有历史行必须保持不变；显式演进只允许追加本次实际执行的版本。比较旧初始化、旧增量链升级结果与新安装的结构等价性。
- 验证重复启动、失败记录、错误校验和、不完整历史和初始化文件篡改；异常不得改变业务数据。
- 运行权限范围、MFA 替换和支付存储回归。不要用默认本地业务数据库制造测试 fixture。

临时参考脚本、测试数据、报告与日志只放在 `.runtime`，不把历史 SQL 测试归档重新加入源码。

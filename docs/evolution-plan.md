# Lumira 开发框架演进方案

2026年10月19日｜基于云端提交 e5912127157da71fa736e5906310f5677dc6ade2 与最终七区架构图

## 结论

采用“模块化单体打牢基础 → 可发行的开发框架 → 多应用复用 → 按需拆服务”的路线。模块化单体可以是长期生产形态，不必为了未来主动增加微服务数量。未来财务、人力资源、行政、企业资源管理系统分别基于框架开发，框架提供基础能力，不内置这些系统的业务规则。

P0～P3表示建设优先级，不表示现有模块可以随意卸载。以下阶段按验收结果和真实需求进入，不给缺乏依据的上线日期。

## 现状：已有基础，以及尚未证明的能力

- 已实现：前端装配边界、后端接口与权限检查、宿主模块、可信同进程插件、公共能力、数据存取、共享数据库与独立文档服务的七区结构；已补充插件依赖检查、动态加载时序、卸载失败处理及事件并发回归。
- 当前宿主为模块化单体；插件与宿主同进程、共享 PostgreSQL。源码边界检查不等于独立 SDK 构建，也不等于不可信插件的安全沙箱。
- 当前本地验收汇总：Java 去重合并后1184项通过、7项受文档服务环境阻碍；前端404项通过、1项条件跳过；有真实HTTP权限及11角色矩阵验证。浏览器页面与热更新尚未完成真实验收，文档导入导出相关路径未验收。已有4900次受控请求样本不能外推生产容量。
- 当前提交尚未推送、合并或部署。本文是演进规划，不把后续目标写成既有能力。
- 现有数据库文档明确全局仅保留初始化基线，不支持旧版本数据库直接升级；“能创建新库”不能代替“可升级已上线应用”。

## 第一阶段｜P0：当前版本稳定可验收

**进入条件：现在。**

工作：
1. 保持七区职责清晰，建立模块依赖白名单与禁止循环规则；接口层检查身份，功能层检查动作与对象范围，前端隐藏菜单不能承担授权。
2. 明确表、文件、迁移和事件的模块所有者。同库也由所属模块控制写入；跨模块通过公开接口或事件访问，逐项登记并收口现有直接跨表访问。报表确需跨域读取时使用约定的只读视图或读模型。
3. 补齐真实浏览器、文档服务、插件加载卸载、失败恢复、权限负例与旧数据读取验收。保持隔离，不为测试通过而改为宿主解析文档。
4. 给当前发行制品固定模块/插件清单、依赖与摘要；清理架构文档中过时的具体业务迁移路线和“稳定 SDK”等超前描述。

**退出验收：** 全部关键用户路径有证据；未通过项有明确阻断或禁用范围；权限越界及插件失败默认拒绝；依赖违规可被持续集成阻断；数据库备份能在隔离环境恢复并核对数据。不能以只通过编译判定完成。

## 第二阶段｜P0/P1：成为真正可复用的开发框架

**进入条件：第一阶段通过，需要交付第一个独立业务应用。**

工作：
1. 从宿主中提取独立版本的公开开发包，只暴露身份上下文、权限检查、模块生命周期、文件/事件等必要契约；插件构建不再依赖整份宿主编译输出。接口与实现分离，支付等领域契约不塞入万能公共包。
2. 提供最小发行版、按需能力清单与独立应用脚手架。用无特定行业规则的示例验证：一个页面、一个API、一组权限、所属数据与迁移、一个事件消费者。
3. 建立框架版本、开发包版本、插件/应用兼容矩阵和弃用窗口。接口、事件有明确版本，优先向后兼容新增字段，破坏性变化并行支持旧版并给出退出条件。
4. 从选定的首个受支持发行版开始保留增量迁移；冻结升级样本库，测试上一受支持版本→当前版本。对于更早数据库另做显式迁移工程，不宣称自动兼容。

**退出验收：** 新应用在独立仓库仅依赖发布包即可构建；不用复制宿主源码或修改私有内部类；插件可独立测试；禁用通知/支付等选配能力后，声明支持的最小组合可启动；升级保留数据与权限，失败可按已演练方案恢复。

## 第三阶段｜P1：支持多个独立应用稳健运行

**进入条件：出现第二个独立应用，或真实部署要求多副本、统一登录及明确服务目标。**

工作：
1. 统一身份支持标准单点登录接入；“是谁”由身份提供方确认，“能在本应用做什么”由应用自己的权限与数据范围决定。登录成功不自动成为各应用管理员；禁用公开注册仍能正常运行。
2. 应用各自拥有业务数据库与发布周期；不通过共用业务表实现复用框架。固定批准插件图的同构多副本先验收，任意插件图动态混跑仍不承诺。
3. 事务内写业务数据与发件箱；消费者以事件标识/业务唯一键实现去重，状态更新与确认尽可能同事务。外部邮件、支付等副作用另用提供方幂等键、对账或补偿，不能声称端到端恰好一次。
4. 采集接口延迟/错误率、数据库连接等待/锁等待、事件积压年龄/重试/死信、插件恢复失败、文档处理时长、资源和费用。为具体应用约定服务目标、可接受数据丢失窗口与恢复时限，再做容量和故障演练。
5. 多租户为可选产品路线。若承诺共享应用服务多租户，必须验证查询、写入、缓存、文件、后台任务、事件、导入导出及审计的租户隔离；组织数据范围不能替代租户边界。

**退出验收：** 两个独立应用验证框架升级兼容；单点登录与权限撤销验证通过；多副本下任务租约、去重、会话与故障恢复通过；代表性数据量与负载达到事先约定目标；完成备份恢复演练。只有需要多租户的发行形态才增加该项承诺。

## 第四阶段｜P2：有证据时选择性拆服务

**进入条件：** 某能力反复需要独立扩容、故障隔离或独立发布，且单体内部优化无法经济地满足目标；拆分收益覆盖运维、网络、数据一致性与团队成本。

- 首选评估文档处理等耗资源且接口清晰的能力；文档服务已经独立，应先完善现有隔离、超时与恢复。通信投递、智能推理等仅在实测触发时评估，不按模块数量拆分。
- 每次只拆一个边界：先固定接口与事件契约及数据所有者，再建立远程适配层、超时、重试、限流、故障降级与可观测性。强一致操作留在同一事务边界；跨服务过程明确最终一致、补偿和对账责任。
- 迁移采用“兼容扩展→回填校验→影子读取→小范围切换→正式切换→保留回退窗口”。避免无保护双写。切换前备份，核对数量、关联、权限和业务不变量；回退前处理新服务独有写入，不能只切回旧流量造成丢数据。
- 回滚应用包与回滚数据库分开设计。破坏性删列、删旧表放到兼容窗口结束后；不可逆变更优先修复前进或从已验证备份恢复，恢复对现有写入的影响需明确。

**退出验收：** 独立部署/回滚、断网与超时、重复/乱序事件、数据迁移与恢复全部通过；实测延迟、稳定性或成本收益成立；能够承担额外监控告警和值守。否则继续保持模块化单体。

## 架构选择与成本原则

| 场景 | 优先选择 | 主要代价 |
|---|---|---|
| 小团队、强事务、发布节奏接近 | 模块化单体＋明确模块边界 | 同进程故障与资源竞争，需要工程约束 |
| 多业务系统分别开发 | 共用框架版本，各应用独立部署和数据 | 兼容矩阵、升级工具与发行维护 |
| 个别任务资源差异大 | 单体＋少量独立服务 | 网络失败、重试、队列与恢复成本 |
| 多团队确需独立交付与扩容 | 逐个边界拆服务 | 分布式一致性、运维和值守显著增加 |

不预先承诺节省百分比或固定机器费用。按相同负载对比计算、存储、网络、监控、备份和维护工时；先保证可靠性，再选择总成本较低的形态。

## 建议先落地的三件事

1. 关闭当前 Office 与浏览器验收缺口，给版本一个可信完成标准。
2. 做独立开发包与最小应用示例，用独立构建证明框架边界。
3. 做首个支持版本的升级、备份和恢复测试，以此决定是否可发布框架版本。

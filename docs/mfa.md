# 二次认证与验证器插件

本文说明新版 MFA 的产品与运行边界。统一实现和隔离环境的主要状态机、插件构建、数据库及HTTP验收已完成；新凭据录入的完整人工界面流程、外部渠道及生产运行分别留证。统一规则以[角色认证设计](role-authentication.md)、[恢复与替换契约](mfa-recovery-contracts.md)及[可靠性要求](authentication-reliability.md)为准。

`plugins/mfa/` 提供 TOTP 验证器与一次性恢复码，identity 宿主管理主验证、角色/全局要求、受限登录挑战、再次验证票据与凭据修订。邮箱、短信、微信和 Passkey 是主登录能力；在有效策略要求 MFA 时，它们全部进入同一二次验证流程。

## 要求来源与首次绑定

有效要求来自全局、实际分配且启用的角色、本人主动启用的 `SELF_ENABLED` 和恢复待办 `RECOVERY_PENDING`。角色视角预览不能改变真实账号的认证要求。

主验证通过后，尚未满足 MFA 的会话不能访问普通后台。已有验证器进入 `MFA_REQUIRED`；首次强制绑定进入 `ENROLLMENT_REQUIRED`。绑定设置和动态码确认使用宿主受限接口，确认之前不会建立完整认证会话。刷新只能恢复本会话的脱敏阶段，不能恢复验证器密钥或凭据输入。

本人在完整登录会话中主动启用 MFA，确认后写入 `SELF_ENABLED`。角色/全局要求下的受限首次绑定只激活凭据，不替用户写入本人主动选择。角色停用或移除仅解除该来源的要求，其余来源仍生效。解绑不能清除全局、角色或恢复待办要求。

## 验证器与敏感操作

用户在 `/dashboard/mfa-authenticator` 查看、绑定和管理本人的验证器。开始设置前使用短时、动作绑定的再次验证票据；根据当前账号策略和已绑定方式，可以使用密码、邮箱验证码、短信验证码或 Passkey。再次验证证明不代替所需的当前 MFA 证明，也不能用于另一账号、会话或动作。

设置返回一次性密钥及 `otpauth://` URI，用户使用验证器应用确认动态码。密钥仅在设置阶段显示，设置有期限；确认成功后一次性展示恢复码，不在浏览器持久存储。更新名称、重新生成恢复码、替换或解绑分别按其动作要求再次验证。重新生成立即使旧恢复码失效。

替换验证器先创建独立、限时的新设置，原验证器及其恢复码继续有效。确认新动态码后，同一事务替换密钥与恢复码、推进因子凭据修订、撤销全部会话和旧挑战，用户随后重新登录。取消、过期或配置修订变化不能删除原验证器。

TOTP 使用六位数字和30秒时间步，已接受的时间步不能重放。验证器密钥使用部署密钥环加密；恢复码与恢复票据保存用途隔离的认证摘要。管理接口不能读取验证器密钥、恢复码或投递凭据。部署必须保留解密既有信封所需的旧密钥。

Passkey 注册、登录和动作绑定再次验证共用 PostgreSQL 分钟桶。默认每分钟发行预算为全局 1000、来源 120、已有会话 10；验证预算为全局 2000、来源 240、已有会话 20，按全局、可信来源、已有会话顺序消费。首次请求先过全局和来源预算，再创建 HTTP 会话；未建立会话时由全局与来源预算保护。可通过 `lumira.passkey.issue-global-per-minute`、`issue-source-per-minute`、`issue-session-per-minute` 及对应的 `verify-*` 配置项调整，所有值限制在 1–10000。当前密码证明继续共用账号级 `PasswordChangeLimiter`，每分钟默认 5 次。

每个会话的每种挑战最多保留 5 个未消费记录，注册、登录和再次验证种类彼此独立。清理任务每分钟运行，单次最多删除 10 个 2000 行批次；如果预算耗尽会记录积压告警。清理间隔和首次延迟可分别通过 `lumira.passkey.cleanup-interval-ms` 与 `lumira.passkey.cleanup-initial-delay-ms` 调整。限流计数在独立事务中提交，即使后续挑战验证或业务事务回滚也不会退还预算。

## 管理与恢复

`/dashboard/mfa-management` 的列表要求全局 `platform:mfa:read`，管理员重置要求全局 `platform:mfa:reset`，并要求操作者在 `platform:users:update` 数据范围内能管理目标用户。列表服务端分页，只展示管理所需的脱敏状态。管理员不能通过管理接口重置自己的验证器，且须满足本人的再次验证和二次认证要求并填写原因。

安全重置撤销目标账号全部会话和旧因子证明，保留原 `SELF_ENABLED`，并写入 `RECOVERY_PENDING`。恢复票据使用256位随机值、15分钟期限和一次性消费；向目标账号当前已验证联系方式投递时，票据在队列中加密。不能安全入队时整个重置回滚，原验证器继续有效。队列接受不表示用户已收到票据。

用户重新完成主验证后进入 `RECOVERY_REQUIRED`，提交有效票据只推进到受限重新绑定阶段；确认新验证器后才清除恢复待办并按当前真实策略完成登录。找回密码、停止角色、切换主登录方式和插件缺失均不能清除恢复待办。错误尝试持久限流，重新登录或切换节点不能恢复已消耗的尝试额度。

离线运维恢复仅用于正常管理员恢复渠道不可用的事故。使用部署中的同版本宿主 JAR 和服务数据库/密钥环境，在应用节点上运行一次性命令；示例中的 JAR 路径应替换为部署固定路径：

```sh
java -jar /opt/lumira/platform-server.jar --offline-mfa-recovery \
  --username admin \
  --operator INC-2026-1042 \
  --reason "All authenticated administrator recovery channels are unavailable"
```

命令读取部署服务管理器注入的 `LUMIRA_DB_URL`、`LUMIRA_DB_USER`、`LUMIRA_DB_PASSWORD`、`LUMIRA_SECRET_KEYS` 和可选 `LUMIRA_SECRET_ACTIVE_KEY`；不要把密钥写入命令行参数、终端记录或工单。部署执行账号须能读取同一受限运行环境，并使用应用数据库账号。数据库账号需具备认证策略锁与目标用户的行锁、MFA要求/验证器/恢复票据、认证挑战、Spring Session、速率记录和邮件队列表的相应读写及删除权限；迁移账号仍单独负责结构变更。运维操作者须有事故单授权并核对目标账号；应用本身会校验目标处于 MFA 保护状态并落独立审计。

若账号有已验证邮箱，命令只把加密邮件任务写入现有队列，不输出票据；此时不得指定 `--ticket-file`。若没有已验证邮箱，必须另加一个绝对路径的全新 `--ticket-file /secure/recovery/admin.ticket`。该文件由运行账号创建为仅所有者可读写（0600）；其父目录也必须由运维预先设为仅受信操作者可访问。将文件安全交付给目标本人后立即销毁运维副本，不复制到日志、工单或共享目录。命令不会在标准输出打印票据。

该操作会保留 `SELF_ENABLED` 与强制要求，设置 `RECOVERY_PENDING`，轮换因子修订并撤销目标账号会话及旧挑战；票据有效15分钟且只可用于受限验证器重新绑定，不能直接建立完整会话。成功后目标仍须正常完成主验证和恢复流程。退出码 5 表示提交结果不确定：不要盲目重复执行或删除票据文件，应先查独立审计和队列/恢复状态，由获授权运维操作者查明结果并记录后续处置。不能直接删除要求表、修改密码或清除本人保护来替代恢复。

## 接口与运行

| 入口 | 职责 |
| --- | --- |
| `/api/account/reauthentication/**` | 本人完整认证下的动作绑定再次验证 |
| `/api/auth/second-factor/pending` | 当前会话的脱敏待验证状态 |
| `/api/auth/second-factor/confirm` | 动态码或一次性恢复码验证 |
| `/api/auth/second-factor/enrollment/start`、`/confirm` | 受限首次绑定或恢复后的重新绑定 |
| `/api/auth/second-factor/recovery/request`、`/verify` | 受限恢复票据投递与消费 |
| `/api/mfa/account`、`/setup`、`/confirm` | 已登录本人状态与主动绑定 |
| `/api/mfa/account/replacement/setup`、`/confirm`、`/cancel` | 原子替换验证器 |
| `/api/mfa/account/recovery`、`/label` | 重新生成恢复码、修改名称 |
| `DELETE /api/mfa/account` | 按当前策略允许的本人解绑 |
| `/api/mfa/manage`、`/{userId}/reset` | 有权限管理员查看与安全重置 |

写请求保留 CSRF、当前授权上下文修订和端点自己的再次验证证明；只读角色预览下禁止凭据管理。端点正文、状态和错误以实际 Controller 与[接口契约](mfa-recovery-contracts.md)为准。

插件缺失或加载失败时，仍需 MFA 的账号安全失败，不能降级成主验证即登录。仍有保护账号、有效凭据、恢复待办或挑战的提供方不能随意停用、卸载或清理数据。固定插件图的多实例部署还须拒绝在线生命周期变更并检查节点 readiness；单实例开发的热插拔不能证明多实例一致性。

## 验收边界

验收使用隔离数据库、合成账号和独立配置。至少覆盖所有允许主登录方式的 MFA 门槛、首次受限绑定、动态码/恢复码重放、原子替换回滚、非密码再次验证、票据失效与恢复待办保留、会话撤销、两节点续接及提供方不可用。

`scripts/mfa-smoke.py` 是历史验收工具；它的 `--passkey-only` 路径仍以旧请求形状调用登录选项（无 JSON DTO 的空 POST），当前端点可能在请求解析阶段返回 415，因此不能把该结果当作当前 Passkey feature gate 或新版 MFA 流程验收。运行前必须核对新版端点、DTO、票据与恢复语义，并确认脚本只操作指定隔离环境。

`scripts/passkey-smoke.py` 验证当前 API 的窄边界：管理员登录和当前设置投影、`{}` JSON 登录选项请求及带 `currentPassword` 的注册选项请求是否到达默认关闭策略并返回 `passkeyFeatureDisabled`，以及凭据列表是否只投影安全字段。它不验证启用策略下的完整注册/断言、MFA 绑定/恢复流程或实体认证器。两个选项请求仍消耗 Passkey 发行预算，注册请求还会检查并消耗当前密码预算；只能对隔离 QA 数据库运行，并让 `LUMIRA_SMOKE_CONFIG` 与 `BASE_URL` 指向同一环境。禁止用主库真实账号做凭据变更测试。合成 WebAuthn assertion 证明服务端签名和状态机边界，不能替代浏览器实体认证器验收。实际渠道送达和生产容灾演练另行记录。

当前验证器插件为1.0.5。V5追加替换槽位的TOTP重放步长，V1–V4不改写；更换确认先按替换用途解密，再按正式凭据用途重加密，在同一事务激活。邮箱OTP加当前TOTP再认证、替换后全部旧会话/旧因子/旧恢复码撤销、实际JAR离线文件恢复及受限重新绑定已在隔离双节点验证。

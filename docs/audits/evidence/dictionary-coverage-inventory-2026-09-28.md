## Implementation boundary and protection status

- V13 belongs to `feedback` and adds nullable `platform_feedback.category`, a format check and recent-category index, plus the five seeded category items. Nullable `NULL` retains legacy uncategorized meaning; stable values are stored on new feedback.
- `DictionaryLookupRepository.policyItems` supplies only enabled dictionaries/items. `FeedbackCatalog` loads the status, priority, category and default dictionary rows from that read-only port and produces a validated server policy. `FeedbackStore.create` checks active priority/category membership before insert; `FeedbackStore.handle` checks configured statuses and derives `handled_at` from the terminal marker.
- `apps/web/src/features/dictionaries/dictionary-items-page.tsx` invalidates `feedback-options`, the sensitive-word `dictionary-options`, and resource-select caches after item mutations. Feedback uses React Query key `feedback-options`; category choices feed form, filters, list tags and detail tags. Missing/disabled category labels fall back to the raw code; null displays as uncategorized. No feedback row is rewritten when an item is disabled or deleted.
- The editor makes the category value read-only for an existing item, and `DictionaryItemService.update` rejects changing that value. This restriction is scoped to `work_order_feedback_category` only.
- Source guards in `DictionaryItemService` and `DictionaryService` protect feedback status, priority, defaults, feedback category, and sensitive-word category; the five consumer dictionary masters cannot be disabled, deleted, or changed from flat structure. `DictionaryItemUsagePort` keeps feedback and sensitive-word reference checks behind dependency injection. These changes are included in the final Maven verify.
- Feedback source changes include `FeedbackDictionaryItemUsageAdapter` for referenced statuses, priorities, and categories, plus a neutral color fallback for newly added priorities. The focused dictionary/feedback service tests passed and the full Maven gate passed.
- Sensitive-word category is a dictionary-backed metadata field. Applied V15 seeds every stored category string (including strings on soft-deleted rows) plus `DEFAULT` and `IMPORTED` with deterministic IDs; it does not rewrite sensitive-word rows. The category lookup endpoint and create/import/filter consumers use enabled items, while display can fall back to the raw stored value. The sensitive-word reference adapter counts only active (`deleted=false`) rows so cleanup is possible after a word is soft-deleted. Severity and action remain fixed security policy values, and the matcher does not consult category.
- **Verification status:** Node 24 typecheck/build and backend Maven verify passed in the shared window (326 tests; 231 passed, 95 skipped, 0 failures/errors). Flyway V1–V15 and `database-schema-smoke.py` passed. Category UI acceptance remains pending because the Mac was locked.
- **Source caveat:** the dictionaries UI locks the structure selector for protected masters. If a protected dictionary were already `TREE`, its structure cannot be repaired from that UI; source alone does not establish whether any deployed protected dictionary has that state. The sensitive category editor allows up to 128 UTF-16 code units to accommodate supplementary Unicode and now validates a 64-code-point limit client-side. Backend sensitive-category create/filter share the dictionary's 64-code-point limit; the 8-case focused category suite passes, including 33 supplementary code points and rejection of 65. Browser-level dictionary form feedback and live-backend behavior remain unverified.
- The dictionary item delete endpoint physically deletes. V13 avoids cross-module foreign keys from dictionaries into feedback; deleted or disabled feedback category codes therefore rely on the raw-code fallback for historic rows. In the UI acceptance, only the exact synthetic QA item created for that test was deleted.

### Profile-field dictionary search: source diagnosis — 2026-09-29

- Existing UI evidence: the visible search placeholder was “搜索名称或编码”; a nonsecret keystroke was attempted, the AX result marked the input value `redacted`, and the picker collapsed before any filtered result could be verified. The temporary draft was discarded and the four built-in fields returned to `4 / 100`. No screenshot file or raw AX node metadata for the typed value is retained. This is a partial UI observation, not a confirmed live request/response reproduction.
- High-confidence source diagnosis: [`profile-fields-page.tsx`](../../../../apps/web/src/features/settings/profile-fields-page.tsx#L35) keys the dictionary `useInfiniteQuery` by `search`; typing calls `setSearch` through the Select's `showSearch.onSearch` ([lines 79–86](../../../../apps/web/src/features/settings/profile-fields-page.tsx#L79)). For a new search key, the query has no result data while its request is pending. The branch at lines 61–62 treats `!dictionaries.data` as a reason to replace the Select with a plain Input. That changes the rendered component while the user is typing, unmounting the Select and closing its popup/focus. The fallback Input is bound to the dictionary code value, not the search text. When query data arrives the Select is mounted again, but its internal search text is not controlled by `searchValue`; this code path can therefore lose the search interaction rather than leave a filtered picker open. `Providers` sets `staleTime`, focus-refetch, and retry defaults but no `placeholderData`/`keepPreviousData` ([`providers.tsx` lines 63–74](../../../../apps/web/src/platform/providers.tsx#L63)); no application-level query default retains prior results for this key transition. The same project’s [`ResourceSelect`](../../../../apps/web/src/platform/components/resource-select.tsx#L15) keeps Select mounted while data is absent, builds options from `query.data?.pages ?? []`, and exposes loading separately (lines 16–26), demonstrating an existing pattern that avoids this pending-state unmount.
- Classification: treat the dropdown collapse as a source-supported product defect with a high-confidence mechanism, consistent with the observed UI. The retained evidence does not identify the exact keystroke at which React remounted the control, so it does not establish a live component trace or prove a network request occurred.
- AX `redacted` is not produced by this page's source; the search state is ordinary local text, and the visible interface contains no redaction logic. With no raw AX metadata or screenshot of the value, the hiding layer cannot be attributed between the native accessibility provider and CUA output sanitization. It is not evidence by itself that the typing action was blocked.
- Minimal repair direction (not applied): keep the searchable Select mounted throughout pending queries, pass an empty/currently cached option list while `data` is absent, and use the loading state; reserve manual text entry for the no-read-permission path. If query errors must permit manual entry, present that fallback without replacing the control on each search-key transition. A future UI recheck can use the documented visible-input `typeText`/paste action with a harmless dictionary code and verify the resulting visible option list; do not inspect DOM state or inject API/UI state.

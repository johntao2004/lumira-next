# 角色权限委派

权限目录的 `editable` 与角色保存使用同一委派契约。改角色本身（名称、启停、数据范围、配额或权限）时，平台权限必须由操作者在全局范围持有。把角色分配给用户时，目录标成调用方范围的权限只要操作者实际持有即可委派，全局权限仍然必须全局持有；因此组织范围的“分配角色”可以分配只含这些范围权限的角色。当前已安装插件提供的权限，只有已经在全局范围持有全部平台权限、并且持有全局 `platform:modules:install` 的操作者才能引导。插件安装权限不能用于委派平台权限、未知权限或已卸载插件的权限，角色预览不能使用插件引导。

`platform:modules:install` 不是较低权限。角色只有在同时包含全部当前平台权限时才能保存这项权限，目录里也只有全局持有全部平台权限的操作者能勾选它。导入插件包、执行安装以及把带有这项权限的角色委派给别人时，操作者同样必须在全局范围持有全部当前平台权限，否则返回 `moduleInstallRequiresPlatformAuthority`。插件引导仍只覆盖已安装插件自己的权限。插件迁移若要写入 `platform_role_authority`、`platform_authority` 或 `platform_user_role`，必须是随发行包公布的初始化脚本；其他脚本在 Flyway 之前被拒绝。进程内插件代码仍以应用数据库账号运行，因此只有完整平台管理员可以安装。

同一次角色创建、更新或分配只读取一次权限目录。新增权限始终按这次快照做委派检查；快照里已经没有的权限返回 `rolePermissionUnavailable`，不会因为随后卸载插件而跳过检查并被写入。角色更新无论是否改动权限，都会重新校验该角色上的有效权限，因此不能只凭 `platform:roles:update` 改名称、停用、收窄范围或配额。插件引导审计 `role.pluginPermission.bootstrap:<authority>` 只记录本次新增的插件权限，保留或移除不再重复记审计，并且引导本身要求操作者全局持有全部平台权限。退役权限只允许保留或移除，不参加分配检查：角色上留下的已卸载插件权限不会使该角色从分配列表消失，也不会阻止把它分配给用户。重新启用角色或扩大其数据范围时，如果仍保留退役权限，返回 `roleRetainsRetiredPermissions`，而不是笼统的拒绝。角色删除与用户角色移除仍严格校验原有有效权限，不使用插件引导，缺少权限时返回 `rolePermissionRevocationDenied`。已经分配、但当前账号不能再委派的角色，用户编辑器仍允许取消勾选。

卸载插件后保留在角色上的授权保持原样，在插件未安装时不进入 `/auth/me` 的有效权限，也不授予访问。重新安装同一插件后，这些保留授权按当前目录重新生效。这是为了避免临时卸载丢数据；若要收回，应在角色上显式移除。会话和菜单只反映当前目录中的有效权限。

角色编辑器在目标角色仍含有当前账号不能委派的有效权限时改为只读，并说明原因，避免勾选后保存才返回委派拒绝。权限树里的保存按钮只保存认证策略。默认注册角色的编辑器只能勾选公开注册允许列表中的权限。

创建角色时，先确认操作者拥有全局 `platform:roles:create`，再检查权限是否属于目录，避免只持有非全局创建权限的账号探测目录成员。

新账号默认角色始终受公开注册允许列表限制，即使公开注册关闭，也不能删除、停用、扩大数据范围或增加列表外权限。修改前必须在公开注册设置中更换默认角色。该限制在委派校验前返回 `registrationRoleInUse`，避免被插件权限错误遮蔽。

角色编辑器、用户编辑器和用户导入分别显示 `rolePermissionDelegationDenied`（缺少委派权限）、`rolePermissionUnavailable`（目录中已不存在的权限）、`rolePermissionRevocationDenied`（删除或移除分配）、`roleRetainsRetiredPermissions`（退役权限仍留在角色上）、`moduleInstallRequiresPlatformAuthority`（安装权限没有和全部平台权限一起持有）与 `registrationRoleInUse`（默认注册角色限制），不再把这些业务拒绝描述为令牌过期。版本冲突和授权上下文变化仍保留原错误代码。用户导入在预检阶段就检查角色委派，不再等到整批提交才回滚。
